# How to test it, and keep testing it

There are four layers. Use them in this order.

## 1. Automated tests (seconds)

```bash
python -m unittest discover -s tests -t . -v      # unit + CLI + real-interpreter tests
python scripts/eval_fingerprints.py --verbose      # scores the fingerprinter on all samples
```

CI (`.github/workflows/tests.yml`) runs both on Python 3.9-3.12 for every push.

What they cover: redaction (including "does it mangle normal text?"), parsing per ecosystem,
normalization, ledger behavior (ranking, fixes, stats, FTS fallback), CLI workflows, git
remote credential stripping, and **real tracebacks generated by running Python and Node** from
different directories.

## 2. Grow the regression set with real errors (2 minutes each, the most valuable habit)

Every time you hit an error in real work:

```bash
# save the raw error output to a file, then:
python scripts/add_sample.py err.txt --lang python --group py-keyerror-user_id
# same error from another machine/branch -> same --group
# same kind of error, different details  -> new --group, same --family
python scripts/add_sample.py err2.txt --lang node --group node-reading-filter --family node-reading-undefined
```

The helper redacts the text, files it under `tests/samples/<lang>/`, updates `manifest.json`
and re-runs the evaluation immediately. A red result means one of two things:

* a **bug** in the parser/normalizer - fix `deadends/fingerprint.py`, keep the sample as the test
* a **wrong expectation** - the two errors really are different; split the groups

Debug a single error with `python -m deadends fingerprint -f err.txt` (shows parse + both normalized forms).

Aim for 3-5 new samples per week, especially from stacks the suite lacks (Go, Rust, Docker, Gradle,
Terraform, TypeScript compiler, Prisma...). Each one is a permanent guard.

## 3. Dogfood on your own projects (the real test)

Daily loop - four commands:

```bash
some_command 2>&1 | tee err.txt                 # something fails
python -m deadends lookup -f err.txt            # 1. seen it before?
# ...try the approach the AI suggested; if it fails and you change course:
python -m deadends add -a "what was tried" --problem "short title" -f err.txt --env lib=1.2.3
# ...when you finally fix it:
python -m deadends update <id> --root-cause "..." --fix "..." --confidence medium
```

Weekly:

```bash
python -m deadends stats            # lookups, hit rate, matches with a known fix
python -m deadends export -o DEADENDS.md   # skim it: does it read like something a new teammate could use?
```

Keep a tally in `docs/DOGFOOD.md` (template included). For each lookup note whether the match was
**relevant**. Hit rate alone can be inflated by irrelevant "similar" matches; relevance is the honest metric.

## 4. Failure drills (once, then after any change to fingerprint.py)

* Paste an error with secrets in it (fake ones) and confirm nothing sensitive shows in
  `python -m deadends list --json`.
* Run `lookup` on an error you have never logged: it must say "No prior record", not invent a match.
* Log the same error twice: the second `add` should warn it was seen before.
* Delete `~/.deadends/ledger.db` (or set `DEADENDS_DB=/tmp/x.db`) and confirm everything recreates cleanly.

## Isolated test database

```bash
export DEADENDS_DB=/tmp/scratch.db     # experiments never touch your real ledger
export DEADENDS_PROJECT=scratch        # skip git detection
```

## Targets for the first month

* eval accuracy stays at 100% as samples grow (regressions caught by CI)
* 30+ real samples across 4+ ecosystems
* lookup relevance >= 70% on your own dogfood tally
* at least 5 "repeat failures caught" you can describe concretely (these become the demo story)
